UFS-R1 자동매매 명세를 “수익 기대값 중심” 개발 문서로 바꾸기

대상 문서: upbit_auto_trading_strategy_spec.md. 이 보고서는 메인 에이전트 리뷰와 별도 gpt-5.5 에이전트의 반대 검토를 합쳐, 실제 개발자가 구현할 수 있고 비개발자도 위험을 이해할 수 있는 수정 방향을 정리한 결론 문서입니다.

1. 결론 요약

현재 명세서는 전략 아이디어보다 안전장치가 잘 잡혀 있어 출발점은 좋습니다. 하지만 실거래에 가까워질수록 “차트 신호를 더 잘 찾는 일”보다 “주문 중복, 손절 실패, 잘못된 백테스트, 숫자 오차를 막는 일”이 먼저입니다.

핵심 합의: 수익을 극대화한다는 말은 승률을 약속한다는 뜻이 아닙니다. 여기서는 큰 사고를 먼저 줄이고, 검증된 조건에서만 거래해 위험 대비 기대값을 높인다는 뜻으로 사용합니다.
가장 먼저 고칠 것 주문 안전성
두 번째 축 검증 단계 분리
전략 점수의 역할 결정이 아닌 설명

메인 에이전트는 원문에서 위험한 지점을 찾았고, 별도 gpt-5.5 에이전트는 각 항목에 대해 “동의/부분동의/반대”로 검토했습니다. 둘의 의견을 합쳐 아래 합의안을 만들었습니다.

4단계 수익 기대값과 개발 가능성 기준으로 합의
5단계 P0/P1/P2 우선순위로 문서 수정 방향 확정

3. 주요 발견별 합의

발견 합의 판단 쉬운 설명 문서 수정 방향
주문 timeout과 identifier 부분동의 주문 버튼을 눌렀는데 화면이 멈췄다고 다시 누르면 두 번 주문될 수 있습니다. 자동매매도 같습니다. 응답이 없으면 새 주문을 만들지 말고, 이미 보낸 주문이 살아 있는지 먼저 확인해야 합니다. 주문 전 identifier를 저장하고 UNKNOWN 상태로 둡니다. timeout 후에는 원래 identifier, 미체결/종료 주문, 잔고와 locked 변화를 조회합니다. 확정 전까지 같은 마켓 신규 주문은 금지합니다.
UPBIT_ONLY와 외부 필터 충돌 부분동의 외부 뉴스나 김치프리미엄 정보는 도움이 될 수 있지만, 그 데이터가 잠깐 끊겼다고 무조건 거래를 멈추면 기회를 놓칠 수 있습니다. 운영 모드를 UPBIT_ONLY, EXTERNAL_OPTIONAL, EXTERNAL_REQUIRED로 나눕니다. 외부 데이터가 unknown일 때 각 모드가 경고, 비중 축소, 진입 차단 중 무엇을 하는지 표로 명시합니다.
캔들 백테스트와 호가 검증 범위 불일치 부분동의 종가만 적힌 가계부로 손님이 줄 서 있던 상황까지 알 수는 없습니다. 캔들 데이터만으로는 호가 잔량, 부분 체결, 실제 미끄러짐을 완전히 검증할 수 없습니다. 검증을 1단계 캔들 기대값, 2단계 실시간 호가 로그, 3단계 페이퍼 트레이딩으로 나눕니다. 호가 검증 전에는 orderbook_imbalance를 점수 가산이 아니라 참고 필터로만 둡니다.
현물 손절의 client-side 위험 동의 손절 감시는 봇이 켜져 있을 때만 작동하는 알람 시계와 비슷합니다. 알람 시계가 꺼지면 손절도 늦어질 수 있습니다. 최악의 경우 손절은 client-side라고 가정합니다. watchdog_heartbeat_sec, max_unprotected_position_sec, 장애 알림, 긴급 청산, 수동 대응 절차를 P0 요구사항으로 추가합니다.
float 기반 가격/수량/수수료 동의 돈 계산을 대충 반올림하면 잔돈이 틀어집니다. 자동 주문에서는 작은 오차도 최소 주문금액, 호가 단위, 잔고 부족 오류로 이어질 수 있습니다. 주문, 잔고, 체결, 수수료, 손익은 Decimal 또는 정수 최소 단위로 처리합니다. API 전송 직전에는 문자열 숫자로 직렬화하고, 지표 계산용 float와 주문용 숫자 타입을 분리합니다.
signal_score_threshold=70 동의 점수가 높다고 돈을 버는 것은 아닙니다. 중요한 것은 수수료와 미끄러짐까지 뺀 뒤에도 평균적으로 남는지가 검증되는 것입니다. 신호 점수는 실거래 결정 기준이 아니라 후보 정렬과 설명용으로 낮춥니다. threshold 70은 “초기 가설/페이퍼 전용”으로 표시하고, 워크포워드 검증 후에만 확정합니다.

4. 추가로 합의한 누락 위험

누락 위험 왜 중요한가 수정 방향
생존편향 지금 살아남은 종목만 과거 테스트에 넣으면 성과가 실제보다 좋아 보일 수 있습니다. 백테스트 시점별 거래 가능 종목, 당시 거래대금, 상장/상폐/유의종목 이력을 반영합니다.
실거래 전 최소 주문 테스트 부족 전략은 맞아도 주문 형식, 최소 주문금액, 호가 단위, 권한 오류 때문에 실제 주문이 실패할 수 있습니다. 주문 생성 테스트 API 또는 최소 권한 dry-run 체크리스트를 P0에 추가합니다.
보안과 운영 책임 경계 API 키 유출이나 비밀값 로그 노출은 전략 손실보다 더 치명적입니다. 출금 권한 금지, 비밀값 로그 금지, NTP 시간 동기화, 알림 채널, 수동 중단 절차를 명시합니다.

5. 우선순위 합의안

개발 순서는 “돈을 벌 것 같은 신호”보다 “돈을 크게 잃지 않게 하는 안전장치”가 먼저입니다. 자동차로 비유하면, 엔진 튜닝 전에 브레이크와 안전벨트를 먼저 확인하는 순서입니다.

P0
실거래 전 반드시 필요한 안전장치
주문 timeout/중복 방지 상태 머신, UNKNOWN 주문 신규 진입 차단, client-side 손절 장애 대응, Decimal/정수 단위 주문 모델, API/잔고/미체결 재대조, 킬스위치.
P1
검증을 실제 시장에 가깝게 만드는 장치
외부 필터 모드 분리, 백테스트와 호가 검증 단계 분리, 페이퍼 트레이딩 합격 기준, 생존편향 제거, 체결/수수료/슬리피지 모델.
P2
전략 성능을 다듬는 장치
신호 점수 가중치 검증, FVG/OB/Trap 개별 이벤트 스터디, threshold 최적화 제한, 외부 뉴스/김치프리미엄 필터 고도화.

6. 개발 가능한 문서 형태 제안

원본 명세서는 설명이 풍부하지만, 구현자가 바로 작업하기에는 정책이 섞여 있는 부분이 있습니다. 아래 구조로 재정리하면 개발 작업 단위와 검증 기준이 분명해집니다.

문서 장 넣어야 할 내용 완료 기준
운영 모드 정의 UPBIT_ONLY, EXTERNAL_OPTIONAL, EXTERNAL_REQUIRED의 차단 규칙 외부 데이터 장애 시 행동이 표 하나로 설명됨
주문 상태 머신 주문 전 저장, SUBMITTING, UNKNOWN, 조회/대조, 신규 진입 차단 timeout이 나도 중복 주문 경로가 없음
숫자 타입 정책 Money, Price, Quantity, Fee, API 문자열 직렬화 주문 직전 호가 단위/최소금액/수수료 검증 가능
손절 장애 대응 client-side 손절 가정, watchdog, 긴급 청산, 수동 대응 절차 봇 장애 중 열린 포지션의 최대 방치 시간을 제한
검증 단계 캔들 검증, 호가 로그 검증, 페이퍼 검증, 소액 실거래 각 단계가 통과해야 다음 단계로 이동

7. 다음 문서 수정 체크리스트

P0 수정 체크리스트

  • identifier는 주문 전 저장하고, timeout 시 재주문 금지로 수정
  • UNKNOWN 주문이 있으면 같은 마켓 신규 진입 금지
  • 손절 감시가 봇 장애 시 실패할 수 있음을 명시
  • 가격/수량/수수료 타입을 Decimal 또는 정수 단위로 변경
  • 주문 생성 테스트와 최소 권한 API 체크리스트 추가

P1/P2 수정 체크리스트

  • 외부 데이터 모드별 hard block 기준 표 추가
  • 캔들 백테스트와 호가 로그 검증을 별도 단계로 분리
  • 생존편향 제거를 위해 시점별 유니버스 재구성 명시
  • signal_score_threshold=70은 검증 전 가설로 표시
  • FVG/OB/Trap 개별 이벤트 스터디 결과를 점수 근거로 연결
